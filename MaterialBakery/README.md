# DeepSeek's Material Bakery

Blender 的**分步烘焙**插件：先挑要烘什么，再设怎么烘，然后烘，最后交付。
和一般"一键烘完拉倒"的烘焙插件不同，这里把**烘焙**和**交付**（导出贴图、建最终材质、
清理材质槽、复制最终物体）拆成两件事 —— 烘完可以先看结果，不满意不用重跑。

> ℹ️ **本版本是独立构建**：不含任何第三方重拓补集成。
> 需要 QuadRemesher 那条 "高模 → 低模 → 投影烘焙" 流水线的话，用另一个私有构建。
> 投影烘焙（Selected to Active）本身仍然完整可用，源可以来自任何高模。

## 安装

**方式一：直接复制文件夹（推荐）**

把 `material_bakery` 复制到 Blender 的插件目录：

| 系统 | 路径 |
|---|---|
| Windows | `%APPDATA%\Blender Foundation\Blender\<版本>\scripts\addons\` |
| macOS | `~/Library/Application Support/Blender/<版本>/scripts/addons/` |
| Linux | `~/.config/blender/<版本>/scripts/addons/` |

然后 `Edit > Preferences > Add-ons`，搜 `Material Bakery` 勾上。

**方式二：装 zip**

- `material_bakery_install.zip` —— Material Bakery 本体

`Edit > Preferences > Add-ons > Install...` 选它即可。
zip 的根目录是 `material_bakery/`。

装好后在 **3D 视图按 N**，侧栏里选 `Material Bakery` 标签页。

## 用法：向导

一共 **4 页**：

```
Targets & Maps  →  Settings  →  Bake  →  Result
```

严格按顺序走，只能上一步/下一步；被跳过的步骤，前进和后退都会一起跳。

**第 1 页 Targets & Maps** —— 烘什么
- 目标模式：按集合 / 单个集合 / 选中的物体
- 集合列表可以逐个勾选，每行显示物体数、缺 UV 数、重叠比例
- 烘焙列表：加类型、**改分辨率（两个框：宽 W / 高 H）**、排序、去重、启停
- 分辨率**不限于正方形**：`W` 和 `H` 分开填，512 x 256 这种窄长贴图照样烘
- 每种类型下面有它自己的参数（通道打包的 R/G/B、AO 距离、UV 层名、法线空间等）

**第 2 页 Settings** —— 怎么烘、存哪
- 预设栏（存/读/删）、**命名方案下拉列表**（选一个就填好模板/连接符/后缀）
- 命名：`Common Parts 1-BaseColor-2k` —— `{size}` 的规则是
  - **正方形**：是 1024 的倍数就写小写 `1k`/`2k`/`4k`，否则写那个数（`512`）
  - **非正方形**：两条边**都是** 1024 的倍数时取**大的那条**写 k
    （2048x1024 → `2k`，1024x4096 → `4k`）；只要有一条不是，就两条边都写完整像素
    （1024x512 → `1024x512`）
  - ⚠ 副作用：2048x4096 与 1024x4096 都会得到 `4k`。同一个集合里放了**同一类型**
    的这两档，就会写出同一个文件名（后烘的覆盖先烘的）—— Checklist 会警告
  - 连接符是 `-` 不带空格
- 输出目录、格式、子文件夹、覆盖、fake user、打包进 .blend
- **采样分两组，每组「低/中/高 + 自定义输入框」**（烘完由事务把场景采样数还原）：

  | | 确定值通道（颜色/粗糙/金属/法线/IOR…） | 需采样的通道（AO / 阴影 / 光路类） |
  |---|---|---|
  | Low | 1 | 16 |
  | Medium | 16 | 64 |
  | High | 64 | 256 |
  | Custom | 按输入框 | 按输入框 |

  确定值通道每个采样算出来都是同一个数，烘 64 遍等于把同一张图算 64 遍 ——
  128 张 2048² 花 21.7 分钟，绝大部分就是这么烧掉的。
  输入框**直接改数字就会自动切到 Custom**，不用先去选下拉。
- **Bake Method**：`Emission + Node Surgery`（默认，任何通道都成立）/
  `Native Render Passes`（不改你的材质；Base Color→Diffuse-Color、Roughness、Normal，
  没有对应 pass 的通道自动退回 Emission 并在报告里说明）
- 边距 + **Adaptive Margin**（两者都有文字标签了，不再有"没有说明的钩"）
- 抗锯齿（关闭 / 超采样 / 放大）
- **Unwrap With SmartUV**（默认关 —— 已经展好 UV 的模型一个字节都不会动）
- UDIM
- **Baked From High-Poly**（投影烘焙）
- 红绿清单：有红色项时 `Next` 被禁用（每一条都有文字说明）

**第 3 页 Bake** —— 进度、当前任务、队列、预计剩余、实时日志、暂停/继续/取消、
确认弹窗（会告诉你大概要出多少张图）
- **烘焙期间整个 Blender 照常可用**：能切窗口、能点按钮、能翻页 ——
  模态 operator 对不处理的事件返回 `PASS_THROUGH`，不再吞掉鼠标键盘
- 队列是**紧凑**的：一行 `完成/失败/剩余` + 当前任务附近几行 + `… N more`，
  128 张贴图也不会铺出一个滚不完的列表
- 日志里**每个任务开始/失败/等待都有记录**，并且**同时落盘**到
  `%TEMP%\material_bakery_last_run.log` —— 就算卡死强杀，事后也能看到现场
  （Bake 页有 `Open Session Log` 按钮直接打开）
- 万一 Cycles 的烘焙 job 不回来了（**2 分钟**没动静）：把它记为失败、
  **保住已经烘好的部分**、剩下的标成 skipped，界面立刻还给你 —— 不用再强杀 Blender
  （2 分钟的依据：实测单张最慢 37.9 秒、平均 10.1 秒）

**第 4 页 Result** —— 交付
- 摘要（成功/失败/跳过）、原材质 ↔ 烘焙材质一键对比
- 贴图列表**按集合分组、可折叠**（一个集合一行：几张、多大、成功没有），
  展开才逐张列出、逐张导出
- 建最终材质（**只有 Principled BSDF 一种** —— 那个"只放贴图"的选项已删掉，
  它出来的材质没接着色器，用户还得自己接）、
  **Add Slot** / **Preview Baked** / **Show Original** /
  **Keep Only Baked (Export Ready)** / **Remove Baked Slot (Undo)**、复制最终物体
- **两个按钮的极性**（容易混，所以标签里写明）：
  `Keep Only Baked` = 删掉**旧**槽只留烘焙材质（导出干净）；
  `Remove Baked Slot` = 删掉**烘焙**槽把原材质还回来（撤销）。两个都可逆。
- **撤销（Ctrl+Z）不会再把面板画崩**：撤销会删掉刚建的材质数据块，
  而会话里握着的引用随之失效 —— 现在每块面板单独兜异常 + 撤销后自动清理失效引用
- **Auto Deliver（默认开）**：烘完自动建材质并**把烘焙槽追加到物体上**
  （不改外观）；**再次烘焙前会自动把多出来的槽收回去**
- 存报告（JSON）

### 从磁盘救回来（烘焙被打断之后）

如果 Blender 卡死被强杀，那些**已经写盘的贴图不会白费**：

- **第 4 页先认"文件里已经烘过的材质"**：交付材质身上带着本插件的标记、
  名字就是集合名，所以**重开文件 / 上次烘完保存过**的情况下，
  第 4 页直接可用 —— 贴图列表、Add Slot、Preview、Keep Only Baked、
  复制物体、导出、存报告全都能点，**不用先扫目录**
- 文件里什么都没有时，才给扫目录那条路：**`Scan Output Folder`**
  （默认扫 Output 设置里的目录；这个按钮**常驻**在 Textures 箱里，随时能重扫）
- **扫完 = 烘完的界面**：自动把材质建好、把烘焙槽挂到物体上
  （跟随 `Auto Deliver` 开关；关掉它的人还是手动那两步），
  所以扫完就能直接 Preview / 收尾 / 导出最终物体
- 文件名按三种时代的写法都能反解（`X-BaseColor-2k` / `XBaseColor-2048` /
  `X-BaseColor - 2048px`），每次烘焙还会在集合目录里写一份 `_mbakery.json`
  **manifest**，以后救援就是精确读取；**手改名也能救**
- **UV 对不对得上会自动判断**并写在面板上：打包 UV 层（`MBAKERY_UV`）还在就是
  `matched`，丢了就是 `missing — textures will not line up`，并给一个
  **`Repack UVs To Match`** 按钮按同样规则重新打包（这是**重建**，报告里会明说）
- 认不出来的文件（比如被改过名）会**列出来**，不会静默丢掉

### 面板上永远能看到版本号

第 1 页顶部有一行 **`v<版本号> · build <打包时间戳>`**。

> 为什么要写这个：装 zip **不会**替换 Blender 内存里已经加载的旧模块 ——
> 我们为此排查过一整轮"为什么修复没生效"。以后看一眼这行就知道装的是哪一版；
> 升级之后**请完全退出 Blender 再打开**。

### 日志：红字也会留档

- 每次烘焙的日志**落盘**到 `%TEMP%\material_bakery_last_run.log`（每行 flush，
  强杀也不丢）；第 3/4 页的 Log 框在没有会话日志时会**把磁盘上那份显示出来**，
  标清"上次运行的日志"，`Open Session Log` 直接打开文件
- **所有红色报错（还有黄色警告）也会写进这份日志** ——
  以前它们只出现在 Blender 界面上，关掉 Blender 就没了，谁也无从查起
- **每个阶段都自带耗时**（2026-09 加）：日志里每一行都长这样 ——

  ```
  [wizard +421.31s | +10.24s] dispatch Baked-BaseColor-2048: done in 10.24s
  [wizard +731.55s | +310.24s] commit transaction: done in 310.24s
  ```

  左边是"距本轮开始"，右边是"距上一条"。烘完卡住时，**哪一段慢一眼就能看出来**：
  派发（Cycles 在烘）、存盘、事务还原（清节点 / 还原引擎与选择）、交付（建材质、
  加槽）各自一行。只要 Blender 写文件，还会多两行 `file write starting / done in Ns`。

## 关键行为

- **一个集合一张贴图**：`Common Parts 1` 一个材质、一套贴图
  （`Common Parts 1-BaseColor-2k.png` / `-Normal` / `-Metallic` / `-Roughness`），
  集合里所有物体共用
- ⚠ **烘焙用各物体现在的 UV：一个字节都不动，也不新建任何 UV 层**（2026-09 改）：
  以前为了让多个物体挤进同一张图，插件会把它们的 UV 打包进互不重叠的格子、
  新建一层 `MBAKERY_UV` —— 那条路**整个删掉了**。原因：手动排的 UV 常常是
  **故意重叠**的（镜像件共用同一块纹理，省贴图空间），打包既治不了这种重叠，
  又平白多出一层、还浪费大量空间（等格子布局里每个物体固定拿 1/(列×行) 的地盘，
  不管它实际占多少）。
  - 代价如实说清：**重叠的两块区域如果需要的内容不同，后烘的会覆盖先烘的** ——
    这是"不动 UV 共用一张图"的固有代价，由你自己把握
  - 第 1 页的"重叠 %"仍然显示，但**只当信息**，不拦你
  - `MBAKERY_UV` 现在**只有一个来源**：第 2 页给"没有 UV 的物体"展 UV 时，
    在 `Unwrap Into` 里自己选了那一项
- **给没有 UV 的物体展 UV**：`Unwrap With SmartUV`（默认关）+ `Unwrap Into`
  选 `Default UVMap` 或 `New MBAKERY_UV layer`；**已有 UV 的物体永远不动**
- **图写盘、材质链接文件**（2026-09 改的默认）：`Pack Textures Into .blend`
  默认**关** —— 烘完的图写到输出目录里，材质指向那些文件；要不要塞进 .blend
  你自己勾。导出贴图在"没有像素数据"时**直接拷贝文件**，所以链接式的图也能
  反复导出。没设输出目录时会明确警告（那种情况图只在内存里、关掉文件就没了）
- **不改用户的材质**：节点手术只在烘焙期间生效，烘完精确还原
  （节点集合、连线数、常量值都逐项比对过）
- **材质槽交付 = 加一个槽，不动原来的**（用户 2026-09 定稿）：
  - 烘焙完，物体上就是**两个材质**：原来的槽一个不动、烘焙材质追加在末尾
  - 想看成色就点 **Preview**（= 把面分配到烘焙槽，就是材质属性里那个 Assign）
  - 满意之后点 **Finalize For Export**：删掉除烘焙槽以外的槽、面索引归 0、
    顺手把贴图 pack 进 .blend 并设 fake user —— **导出时就只有一个材质**
  - 收尾**可逆**：原槽名与逐面索引一直存在物体上，`Restore Original Slots`
    能把原槽重建回来
- ⚠ **烘焙材质里没有 UV Map 节点**（用户自己发现并拍板的）：
  以前材质会硬引用打包层名 `MBAKERY_UV`，而那一层是**按物体**存在的
  （单物体集合不需要打包、被 uv_pack 跳过的物体没有它），于是没那层的物体会
  悄悄退回别的 UV、表面就采样错了 —— 也就是那次"贴上新材质但表面渲染错误"。
  现在贴图节点不接 Vector，自动用物体当前的渲染 UV 层，每个物体都必然用它
  自己那层，不可能错位。（UV 打包删掉之后，这一条更是彻底不成立了。）
- **只动全部烘焙项都成功的物体**：有一个类型失败就不会拿它盖掉原材质
- **同名材质原地覆盖**，不会每次烘焙都堆一堆 `.001`
- **没有材质的物体会被点名警告**（第 2 页清单里的黄色一条 + 报告里的警告）：
  `1 object(s) have no material and Blender will refuse the whole collection: X`。
  实测过：Blender 对"选中的物体里有物体一个材质都没有"的处理是**整批拒绝**，
  错误是 `No active image found, add a material or bake to an external file`，
  而且不说是哪个物体。
  **注意：这一版只警告、不剔除** —— 哪些物体参与烘焙与以前完全一致。
  要给那个物体随便挂一个材质，或把它的集合关掉，否则那一组会整批失败。

## 烘焙过程：不卡、随时能停

这是按用户的反馈重做过的一环，值得单独说：

- **点下 Bake 之后界面立刻可用。** 准备（展 UV / 打包 UV / 建图像）不是先全做完，
  而是**跟着每个任务走**：建第 1 张图 → 烘第 1 张 → 建第 2 张 → 烘第 2 张 …
  `start()` 本身耗时 0.0000s，单步最坏 337ms、平均 65ms
  （32 集合 × 3 张 2048² 的规模实测，见 `tools/measure_bake_memory.py`）。
- **驱动方式是模态 operator**（跟原版 Auto Bake 一样），所以 **ESC 原生就能取消**，
  事件投递也不会被别的弹窗吃掉。
- **第 3 页有独立一行放大的 `Pause` / `Resume` / `Stop`**，队列里把"正在烘的那一张"
  标成 `<- now`；进度条把准备阶段也算进去，全程都在动。
- **内存会提前打招呼**：超过约 2 GB 时运行报告里直接写明
  `96 maps at this resolution will need roughly 6.8 GB of memory while baking`。
  这个数字用的是实测斜率（约 18 字节/像素），不是按分辨率算的名义值 ——
  实测 2048² 每张约 71.6 MB，名义值只有 64 MB；1024² 更夸张，实测 44.7 MB
  对名义 16 MB。
- **运行期间全局撤销和自动保存是暂停的**（2026-09 加，针对"烘完卡死十几分钟"）：
  烘焙期间 Blender 会把文件标记成"有改动"，而自动保存默认每 2 分钟整份重写 ——
  对一个大场景（打包后几个 GB）就是几分钟的磁盘写入，表现正好是"烘完了界面不动、
  内存还是平的"。撤销是同一个毛病的另一面（`undo_memory_limit = 0` 时每一步永久
  保留）。两者只在烘焙期间关掉，**跑完 / 取消 / 失败 / 注销插件 / 换文件都会还回去**
  （实测：来回切 `use_global_undo` 不会清空你的撤销历史）。第 3 页在运行时也会
  写明这一条。
- **`Hide Unrelated While Baking`**（第 2 页 Quality，默认**关**）：把不属于本次
  运行的网格在烘焙期间藏起来，Cycles 就不必为其它几十个集合建几何、装贴图。
  只藏网格 —— **灯光和摄像机永远不藏**（Combined / Shadow 要用光），
  投影烘焙的**源**也永远留着（藏了光线打不到高模，出来是全黑）。
  ⚠ 代价：藏起来的几何不再遮挡、不再投影，所以 **AO / 阴影 / 光路类通道**的结果
  会变（确定值通道不受影响）。Checklist 会点名是哪几个通道受影响。
- **派发每一张之前先刷一次界面**：`bpy.ops.object.bake` 在 GUI 里是**同步阻塞**的
  （实测：调用返回时已经烘完），所以每张图期间界面本来就不动。现在状态行会先写上
  `baking 8/128: X — BaseColor @2048px (last one took 10.2s, ~1220s to go)` 并强制
  重绘一次 —— 卡住的是哪一张、还要多久，看得见。

## Baked From High-Poly（投影 / 重拓补工作流）

低模是烘焙目标，高模是采样源。打开后可以指定源怎么找：

| Sources 选项 | 用来找什么 |
|---|---|
| Hidden Objects | 所有被隐藏的网格 —— 有些流水线是把高模藏起来而不是删掉 |
| Every Other Object | 组外的所有网格 |
| Name Contains | 名字里含某段文字 |
| Selected Objects | 视口里选中的 |

> **⚠ 必须设 Cage Extrusion。** 实测：只设 Ray Distance 时投影光线打不到高模，
> 烘出来是一张**纯黑图而且不报错**。清单里会对"两个都是 0"给出警告。

- 跨版本冒烟（`tests/mb_smoke.py`）在 **3.6.23 / 4.5.13 / 5.2.1** 上都通过：
  注册、44 种类型表、真机烘焙、节点手术、像素正确性、导出、重复导出、UI、注销
- **逐像素对照**：与独立手写的参考烘焙比对，
  `base_color` / `combined` 完全一致（max 0.0000），数据贴图只差 16bit vs 8bit 量化
- **真机投影烘焙**：Selected to Active 采到的是高模的颜色（`[0.953, 0.349, 0.349]`），
  低模自己的颜色是 `[0.349, 0.486, 0.953]`

  不是按尺寸估的

  阶段计时落盘、逐面索引读写、Hide Unrelated 的藏与放（含"用户自己藏的别去动"）、
  采样提醒、写文件留痕

## 已知边界

- **没有 multires 烘焙**。原版的 `multires.normals` / `multires.displacement` 已删除：
  它们走的是另一个操作符（`object.bake_image`），而且从加进来那天起就是坏的
  （`object.bake` 的枚举里没有 `NORMALS`）。它只在"会雕刻"的工作流里才有意义。
- **没有 i18n**，界面只有英文。
- **不做物体导出**（FBX/OBJ/glTF）—— 用 Blender 自带的导出器。
- 对照测试用的是**独立手写的参考实现**，不是原版插件本身
  （原版那条路是模态 operator，无头环境下没有可靠的驱动方式）。
- **原版 Auto Bake 的源码与它的 9 套测试已从工作区移除**（2026-09-21，用户要求
  "只留你的版本"）。之前那 304 项检查里真正还有价值的部分，已经在
  `mb_test_core.py` / `mb_test_parity.py` / `mb_smoke.py` 里以本工程自己的形式重写过；
  剩下的都是针对原版内部实现的断言，跟着原版一起走。
